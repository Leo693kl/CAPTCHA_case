Когда файл нужен двум участникам, один отправляет владельцу точный запрос с входом, выходом и критерием. Владелец изменения фиксирует решение и вносит его один раз.

## Цикл работы

1. Интегратор размещает ветку плана и открывает общую интеграционную ветку `mvp/kapcha-19nov` с проверенным контрактом. Указывает стартовый commit в очереди.
2. Каждый берёт одну задачу, обновляет ссылки на GitHub и ветвится от общего commit. Имена — `feat/t01-demo-evidence`, `feat/t02-incoming`, `feat/t03-card-metrics`, `qa/t04-acceptance`. PR направляются в `mvp/kapcha-19nov`.
3. Исполнитель запускает тесты и сборку, проверяет собственный сценарий, отдаёт PR с отчётом. Сообщает о конфликте интерфейса через комментарий PR с путём и предложенным изменением. По итогам интегратор отмечает фактические статусы и обновляет контракт.
4. Интегратор принимает в порядке T00 → T01 → T02/T03 → T04, сверяет тесты и сборку после слияний. Команда показывает только проверенный commit. Порядок принятия не мешает начать независимые компоненты параллельно.

## Промпт для Codex участника

> Открой репозиторий CAPTCHA_case и подтяни интеграционную ветку. Прочитай AGENTS.md, docs/case.md, docs/09-status.md, docs/14-workflow.md и свой пакет из docs/plans/INDEX.md. Работай по указанному базовому commit в отдельной ветке. Внеси изменения в файлы своего пакета, прогони тесты и сборку. Верни PR с фактическим результатом каждого сценария, ссылками на доказательства и непроверенным. Изменение общего контракта сначала предложи интегратору.
