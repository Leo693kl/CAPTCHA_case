# КАПЧА — разбор первого плана и сборка MVP тремя Codex

19 ноября 2026. Версия 2. Основание — [кейс КРОК](../case.md), переписка «капчи» за 17–19 ноября, уточнения Виктора и проверенный прототип `fafd69a`. Документы первого плана сохранены в `3a91bbc`. Распределение ниже — предложение для трёх аккаунтов Codex. Имена исполнителей можно поменять без изменения границ модулей.

## Как мы работаем

Работаем по схеме HERMES. Этот чат прорабатывает результат, договаривается с Виктором о спорных местах, пишет задачи и формулирует приёмку. Три рабочих Codex получают общий commit и каждый ведёт свою часть. Для передачи достаточно GitHub: исполнителю нужны задание, интерфейс модуля, пример данных, границы файлов и ожидаемое поведение. Любое изменение общего решения уходит в репозиторий до того, как другой исполнитель начнёт на него опираться.

**Решение по базе — расширяем действующий прототип.** В нём уже есть карта трёх клиентов, шесть линз, поиск и фильтры, редактирование людей и связей, история контактов, тёплый путь, бриф, локальный разбор входящих и экран обмена. Сборка прошла, 20 тестов зелёные. Поиск → карточка → изменение → перезагрузка → локальный diff проверены в браузере. Переписывание заставит заново принимать именно эти сценарии и отнимет время у идей команды.

**Образ финала.** Менеджер готовится к встрече. За полминуты находит ЛПР, видит, на ком держатся отношения, использует обратную связь из интервью и выбирает, кому писать и какой вопрос задать. Добавляет новое наблюдение. Карта показывает, откуда оно пришло, пересчитывает значения, обновляет опыт работы с поставщиком и предлагает следующий шаг. Изменение переживает перезагрузку и видно в локальном предпросмотре обмена с CRM КРОК.

## Точные стыки перед началом вёрстки

На старте **A** публикует один общий снимок схемы и два ожидаемых результата на тестовом клиенте. Ни один компонент не вводит собственную версию записи, периода или статуса. Если обнаруживается изменение общего формата, владелец стыка фиксирует его в одной задаче с примером до и после и проводит через общий commit.

| Стык | Вход → выход | Инвариант и проверка |
|---|---|---|
| A → B, входящие | `companyId`, текущая дата, контакты, режим редактирования. Асинхронный `saveInteraction(companyId, draft)` возвращает id сохранённой записи или читаемую ошибку | В черновике есть стабильный `requestId`. Тот же запрос возвращает тот же id. Проверка компании, связей и даты идёт в слое сохранения. Повтор формы не создаёт запись |
| B → A, подтверждение | Разбор текста возвращает кандидата, тип, входные поля и исходный фрагмент. Явное решение сотрудника вызывает сохранение | До подтверждения карта и аналитика не меняются. Запись источника и принятая правка карты сохраняются одним действием. При ошибке форма сохраняет черновик. Смена клиента не отправляет запись в соседнюю компанию |
| A → C, срез карты | `companyId`, календарная `asOf`, люди выбранного среза, связи, взаимодействия, снимки, открытый контакт. Сигналы пересчитываются из среза | Данные после `asOf` исключаются до расчёта. В прошлом редактирование отключено. Источник прошлой информации — снимки людей и касания, связи обозначены как текущие |
| C → A, навигация | Нажатие карточки показателя или линии поставщика передаёт `interactionId` и открывает запись в истории клиента | ID заранее есть в данных. Если запись не входит в текущий срез, показываем причину и предлагаем перейти на подходящую дату |
| A → C, обмен | Сохранённая запись → прежний локальный адаптер → diff выбранного клиента | Один подтверждённый источник даёт одну строку нового взаимодействия. Перезагрузка показывает ту же запись. Выбор другого клиента не переносит изменение |

**Модель.** Расширяем имеющийся `Interaction` необязательными полями из [контракта данных](../03-data-model.md#контракт-для-доработки). К `opened` добавляем `openObservedOn` в формате `YYYY-MM-DD`, чтобы более позднее открытие не попадало в прошлый срез. История поставщика, предпочтения, упомянутые контакты и фрагмент лежат внутри подтверждённого наблюдения. Отдельная сущность поставщика для показа не нужна. Синтетический пример инициативы, возврата к обсуждению или согласования передаётся с датой, явным типом сигнала и исходной записью. При отсутствии свидетельства оставляем статус неизвестным. Старый JSON загружается без добавления обязательных полей.

Поля и сигнатура входа для двух независимых модулей. Интегратор закрепляет их в стартовом commit:

```ts
type InteractionDraft = Omit<Interaction, 'id'> & { requestId: string }
type SaveResult =
  | { ok: true; interactionId: string }
  | { ok: false; error: string }

type SaveInteraction = (companyId: string, draft: InteractionDraft) => Promise<SaveResult>

type MapSlice = {
  companyId: string
  asOf: string
  historical: boolean
  selectedPersonId: string | null
  people: readonly Person[]
  relations: readonly Relation[]
  interactions: readonly Interaction[]
  snapshots: readonly PersonSnapshot[]
}
```

**Правила подсчёта.** Соседние окна по 30 календарных дней, текущий день включён, пересечения между окнами нет. Показатель компании считается по компании, показатель человека — по человеку. В открываемости знаменатель включает только письма с измеренным статусом, известным на выбранную дату. В упоминаемости знаменатель — подтверждённые наблюдения данной компании за период, числитель для карточки — сколько из них упоминают выбранного человека. Одна запись учитывает упоминание человека один раз. Для сигнала тёплого ЛПР берём роль ЛПР, теплоту от 4 из 5 и касание в последние 90 календарных дней включительно. Оба порога — значения демонстрации, видимые в объяснении.

**Доказательство силы связи.** В контрольном сценарии выставляем предлагаемую силу по числу разных подтверждённых свидетельств для конкретной пары из одной компании: `min(5, 1 + N)` при `N > 0`. Повтор того же источника не увеличивает число. При отсутствии свидетельств предложение не создаётся. Карточка показывает использованные записи, прежнюю оценку и предложенную. Скорость согласования выводится отдельно как разность дат запроса и согласования для одного решения, например 1–4 ноября — 3 календарных дня. Изолированная фраза «я решу» даёт повод проверить роль, сила связи из неё одной не рассчитывается. Это демонстрационное правило, точность на реальных данных не измерялась.

**Контрольный набор для A, B и C.** По состоянию на 19.11 у Александра Белова из банка три письма с измеренным статусом, два из них открыты. Четвёртое без статуса исключается, ожидаем **2/3 = 67%**. Из двух наблюдений одно упоминает Белова. Добавляем обратную связь с ещё одним упоминанием и получаем **2/3** вместо **1/2**, открываемость остаётся **67%**. Причина смены поставщика и источник появляются в нужной карточке. При повторе запроса счётчики сохраняют значение. У второго клиента нет измеренных писем и отображается «Нет данных». Для демонстрации риска один ЛПР выполняет оба условия, у второго теплота от 4, но последнее касание старше 90 дней, остальные не проходят пороги. Новое касание ко второму снимает сигнал. Эти числа — ожидаемые для задания, а данные в код ещё предстоит добавить.

**Вёрстка.** Эталон — [текущая карта](../after/final-map-bank.png), [карточка](../after/final-person.png) и [дизайн-контракт](../12-design-contract.md). В главном представлении — граф, фильтры, легенда и краткая строка показателей. Поставщики раскрываются рядом с графом, без добавления узлов в раскладку людей. Правая карточка показывает сначала решение, последнее касание и следующий шаг, ниже — источники, динамику и историю. «Входящие» используют имеющиеся кнопки, поля и токены. Для компонентов передаются пустое состояние, ожидание, ошибка, длинное значение, историческая дата и работа с клавиатуры. Проверяем 1366×768 и 1920×1080, а также узкое окно на обрезание карточки. В базовом HTML нужны название и короткое объяснение того, что делает демо при включённом JavaScript.

## Три аккаунта и один порядок слияния

| Аккаунт | Зона записи | Первые 30 минут | Что сдаёт |
|---|---|---|---|
| **A — Виктор / интеграция и данные** | `src/types.ts`, `src/App.tsx`, `src/api/crmApi.ts`, `src/lib/crmDiff.ts`, `src/data/crm.json`, `src/components/Integration.tsx`, общие документы | Поднимает общую ветку, закрепляет сигнатуры и один пример. Объявляет SHA и ссылку на контракт. Проверяет базовый сценарий | Сохраняемая запись, согласованный срез, синтетические сценарии, подключение модулей, локальный diff и финальный commit |
| **B — входящие и бриф** | `src/components/Incoming.tsx`, новый редактор, `src/lib/llmExtractor.ts`, `src/components/MeetingBrief.tsx`, тесты разбора | Берёт пример записи, готовит распознавание, состояния формы и проверку источника. Стартует по данным примера, не ждёт графа | Форма, подтверждение, блок конкурентного опыта и рекомендация для брифа. Отдельная ветка `feat/kapcha-evidence` |
| **C — граф, аналитика и экран** | `src/components/MapSurroundings.tsx`, `src/components/TimeControls.tsx`, `src/lib/signals.ts`, новый компонент показателей и чистые функции метрик, локальные стили карты и их тесты | Берёт тот же пример и ожидаемые числа. Готовит представление и проверку нуля, отсутствия данных и периода | Показатели, линия поставщика, динамика, интенсивность и сигналы. Отдельная ветка `feat/kapcha-map` |

Два представления конкурентного опыта имеют разные задачи. **B** делает запись, её содержание в брифе и ссылку на источник. **C** делает визуальную линию у графа. **A** связывает их по одному id. Ни B, ни C не меняют `App.tsx` или общие типы. В примере на фазе старта A может передать временные данные через точные props. К слиянию оба потребителя читают один настоящий срез.

1. **A фиксирует общий старт.** Запись в [очереди](INDEX.md) содержит базовый SHA, ветку `mvp/kapcha-19nov`, владельца и путь к документу. Все участники проверяют совпадение входного commit. Эта ветка должна быть доступна всем аккаунтам, прежде чем они смогут передавать PR друг другу.
2. **B и C работают одновременно.** У каждого задача, файлы и два ручных примера. Проблему на стыке оформляем комментарием в PR с четырьмя полями: что требуется, какой файл, пример входа и ожидаемый выход. A подтверждает изменение одним общим commit. Остальные подтягивают его в свои ветки.
3. **A подключает два PR по очереди.** Сначала форма и сохранение записи, затем карточка и метрики. После каждого слияния сборка, тесты и фактический прогон своего шага. C может проверять отображение раньше по примеру данных. B может проверять форму и парсер раньше графа.
4. **На выпуске A ведёт приёмку, B и C чинят свои зоны.** PR включает краткий отчёт из [порядка работы](../14-workflow.md) и проверенные сценарии. Если одна ветка опаздывает, продолжаем интеграцию прошедших частей и показываем точный остаток по идеям из таблицы. Неработающий кусок не помечаем завершённым.

## Как уложиться в сегодня

| От старта совместной работы | Результат | Как понять, что движемся |
|---|---|---|
| 0–25 мин | Общая версия, договорённый интерфейс, один контрольный набор | A отдаёт SHA, B и C открывают свои ветки |
| 25–90 мин | Форма и алгоритмы на примере, компоненты собраны параллельно | Запись проходит проверку, браузер показывает правильные исходные числа и пустой случай |
| 90–165 мин | Сквозной сценарий на общей ветке и все функции из принятого объёма по одному разу подключены | Сохранение → история → вычисление → визуальное обновление → перезагрузка → diff |
| 165–225 мин | Приёмка, устранение дефектов и репетиция | Два кликабельных размера, переход к другому клиенту, рабочая production-сборка, сценарий на 2 минуты |

Первоначальная оптимистичная оценка — **3 ч 45 мин**. Пересчёт по нагрузке и условия для полного объёма приведены в [разборе перед утверждением](2026-11-19-review.md). Этот график отсчитывается с момента, когда все три аккаунта могут работать от общей ветки. Последние 45–60 минут оставляем под исправления и выпуск. Если время сжимается, снимаем второстепенную вёрстку, анимацию и дублирование графиков, объединяем компактные показатели в один модуль. Для нужных идей остаётся минимальный проверяемый сценарий. Готовность коллективной сборки определяется прогоном, а не временем в таблице.

## Что должно поразить жюри

1. Открываем клиента и показываем реальную проблему на синтетическом примере: у команды один тёплый ЛПР, а часть контактов устарела.
2. Вводим короткий протокол или обратную связь, принимаем предложение. Граф сразу объясняет связь, появляется линия конкурента с причиной смены, меняется счётчик.
3. Открываем бриф и показываем следующий шаг с конкретным вопросом и источником. Меняем дату, видим прежнее состояние, возвращаемся в текущий срез.
4. Перезагружаем страницу, открываем предпросмотр обмена. Коротко объясняем, что существующая CRM дала карте, что команда добавила и что можно вернуть.

Выпуск принимается при действующих семи базовых сценариях, проверенном проходе выше, согласованном клиенте и дате везде, измеренном нуле отдельно от отсутствия данных и отсутствии дубля при повторной отправке. Смена клиента, длинный текст, клавиатура, историческая дата и отказ записи проверяются отдельно по [чек-листу](acceptance.md). Сборка и чек-лист привязаны к одному итоговому commit.
