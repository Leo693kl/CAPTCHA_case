## Как объединяем работу

1. Виктор открывает **локальную папку клона** через Open Folder в Codex. На его Mac это `/Users/mak/Documents/Codex/2026-11-19/new-chat/CAPTCHA_case`. В существующем клоне `origin` уже настроен. Ветка `mvp/kapcha-19nov` создана локально, её можно отправить из аккаунта с правом записи:

   ```bash
   git switch mvp/kapcha-19nov
   git push -u origin mvp/kapcha-19nov
   git rev-parse HEAD
   ```

2. Интегратор передаёт точный стартовый SHA команде. B и C в своих клонах запускают `git fetch origin`, затем создают отдельную ветку от этого SHA через `git switch -c ИМЯ_ВЕТКИ SHA`. На одном компьютере используют разные worktree, чтобы Codex не меняли ветку друг у друга. При работе со своих аккаунтов и компьютеров достаточно отдельных клонов.
3. B и C отправляют свои ветки и открывают PR с базой **`mvp/kapcha-19nov`**. Участники без права отправлять ветку в исходный репозиторий могут работать в собственном форке и открыть PR из него, если правила репозитория это позволяют. Интегратор принимает B, затем C, подключает компоненты в `App.tsx` и проверяет общую сборку. После общей приёмки открывает один PR из `mvp/kapcha-19nov` в `main`.
4. Если публикация временно недоступна, команда может начать с общего Git bundle. В существующем клоне выполнить `git fetch /путь/CAPTCHA_case-start.bundle refs/heads/mvp/kapcha-19nov` и создать свою ветку от `FETCH_HEAD`. Сравнить его SHA со стартовым. Bundle переносит историю и ветку, а `origin` по-прежнему указывает на GitHub. При восстановлении доступа отправляются те же коммиты. Слияние идёт штатно через Git.

Публикация общей ветки и изменения доступа делаются через аккаунт с нужными правами. На старте проверить `git remote -v`, `git status --short --branch` и `git rev-parse HEAD`. Для запуска взять Node 22, pnpm 10 и выполнить `pnpm install --frozen-lockfile`, `pnpm dev`. Перед PR прогнать `npm test` и `npm run build`. В отчёте нужны стартовый SHA, файлы, проверенные клики и их фактический результат, оставшиеся дефекты и изменение контракта, если оно понадобилось.

## Общий контракт на старте

Типы уже лежат в [src/types.ts](../../src/types.ts). Заготовка для ручного прогона — [demo-interview.json](demo-interview.json). Это черновик для проверки ввода, он не должен присутствовать в исходной истории банка до нажатия «Сохранить».

| Граница | Кто отвечает | Что получает вызывающая сторона |
|---|---|---|
| Сохранение | A реализует `SaveInteraction`, B вызывает | `companyId`, черновик с устойчивым `requestId` и необязательное подтверждённое изменение роли/силы. Результат — ID одной сохранённой записи или русская ошибка. После ошибки запись и роль/ребро прежние. Повтор с тем же ключом в той же компании возвращает тот же ID |
| Чтение | A передаёт `MapSlice`, B и C читают | Один клиент, дата, выбранный контакт, снимки, взаимодействия и связи. Существующие связи остаются текущими при просмотре снимка прошлого. Все выводы из наблюдений считаются по дате среза |
| Открытие источника | C и B вызывают `onOpenSource(interactionId: string): void`, A подключает | Приложение находит запись в компании и срезе, открывает карточку её автора-контакта и выделяет запись. После перехода назад возвращает пользователя к исходной карточке или линии. При недоступной записи даёт пояснение |
| Изменение контракта | Запрашивает исполнитель, коммит делает A | Предложение в PR содержит имя файла, пример входа и ожидаемый выход. Остальные подтягивают один общий commit. До него используют текущие типы и проверочный пример |

Правила времени, подсчёта и ожидаемые числа находятся в [модели данных](../03-data-model.md#контракт-для-доработки) и [разборе показа](2026-11-19-review.md). На запуске проверь сценарии ввода, легенду и тур, а также объяснение источников и обновления по [S7–S9](acceptance.md). Только A редактирует общие типы и набор банка. Участники могут держать маленькие примеры в собственных тестах. Текст можно обработать в браузере, автоматические вызовы внешнего API не требуются.
